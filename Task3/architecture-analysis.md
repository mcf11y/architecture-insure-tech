# Анализ проблем и рисков текущей архитектуры InsureTech

В ближайшее время количество подключённых страховых компаний увеличится с пяти
до десяти. Одновременно ожидается рост числа клиентов и оформленных страховок.
Текущая схема синхронных REST-взаимодействий может стать ограничением для такого
роста.

## 1. Зависимость от внешних API

Для формирования списка продуктов `ins-product-aggregator` обращается ко всем
страховым компаниям и ждёт их ответы.

Проблемы и риски:

- время ответа определяется самой медленной страховой компанией;
- ошибка или тайм-аут одного API может повлиять на весь агрегированный ответ;
- после подключения ещё пяти компаний увеличатся число соединений, нагрузка и
  вероятность частичных ошибок;
- повтор запроса приводит к повторному обращению ко всем страховым компаниям;
- недоступность `ins-product-aggregator` блокирует получение актуальных
  продуктов другими сервисами.

## 2. Периодическое получение каталога

`core-app` запрашивает продукты каждые 15 минут, а
`ins-comp-settlement` — один раз в сутки.

Проблемы и риски:

- локальные копии каталога могут содержать устаревшие данные;
- сервисы могут одновременно работать с разными версиями тарифов;
- запросы выполняются даже при отсутствии изменений;
- ошибка ночного обновления оставляет `ins-comp-settlement` без актуальных
  данных ещё на сутки;
- при увеличении количества реплик одновременные запросы создадут дополнительный
  всплеск нагрузки.

## 3. Суточная выгрузка оформленных страховок

Раз в сутки `ins-comp-settlement` запрашивает у `core-app` все страховки,
оформленные за день.

Проблемы и риски:

- объём ответа и продолжительность обработки будут расти вместе с бизнесом;
- тайм-аут потребует повторной передачи всего набора данных;
- при частичной обработке сложно определить, какие записи уже сохранены;
- сбой задания задержит подготовку взаиморасчётов;
- ночная выгрузка создаёт пиковую нагрузку на `core-app` и его базу данных.

## 4. Сильная синхронная связанность

Сервисы зависят от доступности и скорости друг друга непосредственно в момент
REST-вызова.

Проблемы и риски:

- отказ одного компонента распространяется по цепочке вызовов;
- медленный ответ удерживает соединения и рабочие потоки вызывающего сервиса;
- массовые retry могут дополнительно перегрузить восстанавливающуюся систему;
- сервисы сложнее масштабировать и обновлять независимо;
- отсутствует буфер, который мог бы принять нагрузку во время кратковременного
  всплеска или недоступности потребителя.

## 5. Согласованность и надёжность данных

Использование локальных копий требует контроля доставки и порядка изменений.

Проблемы и риски:

- обновление может быть потеряно при сетевой ошибке;
- повторная передача может привести к дублированию данных;
- более старое обновление может перезаписать новое;
- отсутствует простой механизм повторного получения пропущенных изменений;
- невозможно быстро убедиться, что все сервисы получили одинаковую версию
  каталога.

## Итог

Основные ограничения связаны с синхронным ожиданием внешних систем,
периодическими полными запросами и суточными пакетными выгрузками. При росте
числа страховых компаний и клиентов это приведёт к увеличению задержек,
каскадным отказам, устареванию локальных данных и росту нагрузки на
`ins-product-aggregator` и `core-app`.

Наиболее критичны три взаимодействия:

1. получение каталога `core-app` из `ins-product-aggregator`;
2. получение каталога `ins-comp-settlement` из `ins-product-aggregator`;
3. получение оформленных страховок `ins-comp-settlement` из `core-app`.

## Краткое описание решения

В архитектуру добавляется общий Event Streaming на Apache Kafka.

- `ins-product-aggregator` публикует изменения каталога в виде событий
  `ProductCatalogUpdated`;
- `core-app` и `ins-comp-settlement` независимо получают эти события и обновляют
  свои локальные данные;
- после оформления страховки `core-app` публикует событие `PolicyIssued`, которое
  получает `ins-comp-settlement`;
- для надёжной публикации `PolicyIssued` применяется Transactional Outbox:
  страховка и событие сохраняются в `core-db` одной транзакцией;
- синхронный REST остаётся только для операций, которым требуется немедленный
  ответ.

Так сервисы перестают периодически запрашивать полные наборы данных и могут
работать независимо при временной недоступности друг друга.
