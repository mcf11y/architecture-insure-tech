# Технологическая архитектура InsureTech — to-be

Этот документ содержит пояснения к схеме
`InureTech_технологическая архитектура_to-be.drawio`. На самой схеме оставлены
только компоненты, зоны доступности, основные связи и короткие технические
пометки.

## Требования

- Доступность приложения: 99,9%.
- Работа круглосуточно во всех часовых поясах.
- RTO: не более 45 минут.
- RPO: не более 15 минут.
- Сопоставимое время загрузки страниц для пользователей из разных регионов.
- Текущий объём данных: 50 GB.
- Система должна выдержать рост нагрузки после рекламной кампании.

## Итоговая архитектура

Приложение размещается в Yandex Cloud в трёх зонах доступности:

- `ru-central1-a`;
- `ru-central1-b`;
- `ru-central1-d`.

Используется один региональный Yandex Managed Service for Kubernetes. Его
управляющая часть работает в конфигурации HA master, а worker nodes распределены
по трём зонам. В каждой зоне находится node group и реплики приложений
InsureTech.

Для базы данных используется один кластер Yandex Managed Service for PostgreSQL
из трёх хостов: текущий master и две quorum-реплики, размещённые в разных зонах.

## Путь пользовательского запроса

1. Браузер получает адрес сервиса через Cloud DNS.
2. Статические файлы сайта — React, JavaScript, CSS и изображения — отдаются
   через Cloud CDN.
3. Если файла ещё нет в кеше CDN, он загружается из Object Storage.
4. API-запросы поступают на Application Load Balancer.
5. Балансировщик направляет запрос только в доступную зону и только на готовые
   pod’ы приложения.
6. Приложение обращается к текущему master PostgreSQL по приватной сети.

Cloud CDN уменьшает влияние географического расстояния на загрузку фронтенда:
пользователь получает статические файлы из ближайшей точки присутствия CDN.

Персональные ответы API не кешируются. К ним относятся данные профиля,
документы, история заявок и оформленные страховки. Для таких ответов применяется
`Cache-Control: private, no-store`.

## Kubernetes и отказоустойчивость

### Почему используется один региональный кластер

Региональный кластер имеет единые API, namespace, настройки, сетевые сервисы,
секреты и процесс деплоя. Это проще эксплуатации трёх независимых кластеров.

HA master состоит из экземпляров control plane в трёх зонах. При отказе одной
зоны оставшиеся экземпляры продолжают управлять кластером. Worker node groups
также размещаются в трёх зонах, поэтому работающие pod’ы остаются доступны.

Три независимых кластера дали бы более сильную изоляцию, но потребовали бы
отдельного деплоя, синхронизации конфигурации, межкластерной маршрутизации и
отдельного механизма переключения трафика. Для заданной доступности 99,9% такая
сложность не требуется.

### Размещение pod’ов

Для каждого критичного приложения поддерживается не менее трёх реплик.

- `topologySpreadConstraints` распределяет реплики по зонам.
- Pod Anti-Affinity не позволяет разместить все реплики на одном worker node.
- PodDisruptionBudget сохраняет минимум две доступные реплики при плановых
  обновлениях и обслуживании.
- Readiness probe `/health/ready` определяет, можно ли отправлять запросы pod’у.
- Liveness probe `/health/live` перезапускает зависший контейнер.
- Startup probe `/health/startup` даёт приложению время на запуск.

## Стратегия масштабирования

Для stateless-приложений используется горизонтальное масштабирование.

- HPA увеличивает или уменьшает количество pod’ов в зависимости от CPU, памяти
  или прикладной метрики нагрузки.
- Cluster Autoscaler добавляет worker nodes, если новым pod’ам не хватает места.
- После снижения нагрузки лишние pod’ы и worker nodes удаляются.

Горизонтальное масштабирование предпочтительнее постоянного увеличения размера
одного сервера: несколько реплик одновременно повышают производительность и
отказоустойчивость.

Вертикальное масштабирование используется для подбора ресурсов master Kubernetes
и PostgreSQL: vCPU, RAM, размер и производительность дисков.

## Балансировка и failover

Application Load Balancer работает в трёх зонах в режиме active-active. Все
здоровые зоны одновременно принимают трафик.

ALB выполняет HTTP health check `/health/ready`. Если pod или вся зона перестаёт
отвечать, соответствующие endpoints исключаются из балансировки. Пользователь
продолжает обращаться к тому же DNS-имени; ручное переключение не требуется.

Сценарии:

- Отказ pod’а: Kubernetes запускает новую реплику, Service использует остальные
  Ready pod’ы.
- Отказ worker node: pod’ы запускаются на других nodes.
- Отказ зоны: ALB направляет трафик в две оставшиеся зоны.
- Рост нагрузки: HPA увеличивает число pod’ов, Cluster Autoscaler добавляет
  nodes.

## PostgreSQL

Кластер состоит из трёх хостов:

- один текущий master принимает запись;
- две реплики получают поток WAL;
- каждый хост находится в отдельной зоне.

Managed PostgreSQL использует синхронную quorum-репликацию. Транзакция
подтверждается после записи WAL на master и необходимую quorum-реплику. Поэтому
подтверждённая транзакция хранится как минимум в двух зонах.

При отказе master наиболее актуальная реплика автоматически становится новым
master. Приложение должно повторно устанавливать оборванные соединения с базой.

Для допустимых read-only операций можно использовать реплики. Операции
оформления страховки и изменения клиентских данных выполняются через master.

## Backup, WAL, PITR, RPO и RTO

Managed PostgreSQL создаёт автоматические резервные копии. Копии и WAL хранятся
в объектном хранилище отдельно от дисков базы данных. Срок хранения — 14 дней.

- WAL — журнал всех изменений PostgreSQL.
- PITR позволяет восстановить базу на выбранный момент времени до ошибочного
  удаления или повреждения данных.
- При отказе master или одной зоны RPO подтверждённых транзакций близок к нулю,
  поскольку запись уже присутствует на quorum-реплике.
- При логической ошибке PITR обеспечивает точку восстановления новее требуемых
  15 минут.
- Автоматическое переключение master занимает минуты и укладывается в RTO
  45 минут.

Полное восстановление 50 GB из backup необходимо регулярно проверять отдельным
restore-тестом. Только такой тест подтверждает фактическое выполнение RTO.

## Решение по шардированию

Шардирование не применяется. Объём 50 GB невелик для PostgreSQL и не оправдывает
сложность распределения данных между несколькими независимыми базами.

Сначала используются:

1. оптимизация запросов и индексов;
2. вертикальное масштабирование;
3. read-only реплики;
4. при необходимости — секционирование крупных таблиц внутри PostgreSQL.

К шардированию следует возвращаться только после измеримого достижения пределов
одного PostgreSQL-кластера.

## Мониторинг

Для контроля доступности необходимы метрики и оповещения:

- доступность ALB и количество здоровых endpoints;
- HTTP `5xx`, RPS и пользовательская latency p95/p99;
- Ready-состояние pod’ов и число перезапусков;
- CPU, RAM, диск и количество соединений PostgreSQL;
- replication lag;
- успешность и возраст последнего backup;
- результат регулярного restore-теста.
